基准提交：`0c9ddcd`；2026-11-27，本地 Testcontainers，MySQL 8.0、Redis 7-alpine，容器数据独立于用户数据。执行：在 `kuros-backend` 使用 Java 21 运行 `mvn -q -Dtest=InteractionMySqlIntegrationTest test`。5 项通过，其中新增旧快照与取消交错、窗口补齐和同时间排序分页。并发测试在 MySQL 查询之后暂停线程，删除关系并执行真实 Redis 失效，再恢复回填，验证旧快照未安装。窗口测试用数据库删除和缓存失效模拟提交后路径；分页测试针对 repository 查询，不是历史列表 API 的端到端测试。当前仓库未发现点赞历史列表接口，不能据此声称接口验收完成。

## 小规模对照

同一进程顺序执行：20 用户、4 帖子、每用户 4 个点赞、200 次批量请求，每次 4 帖，单线程，冷缓存开始；收藏均为空。前版使用改造前批量方法的两次 repository 查询和结果映射，后版调用当前 `findStatesFor`。两者使用相同数据库和请求序列，非两个完整版本部署。Hibernate `prepareStatementCount` 计数 SQL 预备语句，用作本实验查询数；延迟为 Java 服务层计时，包含数据库和 Redis 往返，不包含 HTTP。采用排序后的 nearest-rank 分位数，无预热剔除。

| 指标 | 前版路径 | 后版路径 |
| --- | ---: | ---: |
| SQL 数 | 400 | 220 |
| Redis DB key 总数 | 3 | 43 |
| Redis used_memory 字节 | 1,301,488 | 1,372,416 |
| P50 / P95 / P99（微秒） | 4,033 / 6,280 / 9,032 | 4,241 / 10,023 / 12,103 |

Redis 总内存包含服务开销、分配器及前序测试残留的 3 个 key，差值 70,928 字节不能当成精确的单 key 成本。新增 40 key 对应 20 个窗口及 20 个 ready 标记。20 次冷回填、180 次窗口命中是按此固定请求序列和 SQL 数推断，并非 Redis 全局 hit rate；该负载全部命中近期窗口，不能代表混合未点赞或历史点赞。前版批量查询不读 Redis，因此全局命中率不适合直接对比。后版 P95 包含 20 次冷回填，且顺序执行、样本少、未做多轮统计；不能据此推断生产性能改善。

额外模拟 20 次失效及窗口重建（未计 MySQL 写事务）：20 条查询，P50 7,709 微秒，P95 9,894 微秒；窗口仅 4 条。每次实际提交后重建都产生一次近期列表查询，窗口越大通常读取和传输成本越高，需在目标规模验证。版本键 TTL 实测为 -1；本实验触及 20 用户和 1 帖会留下 21 个版本键，不随窗口 TTL 过期。长期成本随被写过的用户及帖子基数增长，且本实验未测大基数内存或淘汰策略。

机器为 i9-14900HX、32 逻辑处理器，物理内存约 15.6 GiB；测试启动时可用约 4.0 GiB，Docker Desktop 报告约 7.8 GiB 内存。测试结束后 CPU 三次采样约 9.0%、13.1%、1.9%，并非测试期间连续负载指标。未控制后台负载，结果仅用于复现与发现方向，不能作为容量结论。仍需目标并发、更多数据、冷/热及负例混合负载、多轮独立运行、真实历史接口和端到端指标。
