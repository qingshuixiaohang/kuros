# 互动受理和恢复的边界

适用范围为 #185 和 #188 的后端变更。HTTP 入口不使用 transactional outbox。
RocketMQ 单 Broker 的确认以 `SYNC_FLUSH` 为前提；Compose 中已设置该值，其他部署必须自行保证相同配置。
同步发送只有 `SEND_OK` 才表示已确认，刷盘超时或连接中断等结果不明的情况返回未知。单 Broker 的确认不提供副本容灾。

操作编号通过数据库唯一约束绑定用户、帖子和操作类型。发送结果明确拒绝时会清除本次新建的未受理绑定；
异常或未知时保留绑定。绑定不是消息发送 Outbox：它不自动转发尚未确认的操作。关系、计数及已应用记录在同一事务中提交；
提交后 Redis 失效失败时，数据库保留待失效标记，由恢复任务继续处理。操作查询只向所属用户报告 `APPLIED` 或 `UNKNOWN`，
已提交业务不会因缓存故障被报告为失败。

绑定在发送之前写入 MySQL，明确拒绝后再删除；因此该路径不改变点赞、收藏及计数业务数据，但不满足
“Broker 不可用时完全没有 MySQL 写入”的严格字面要求。绑定写入与清除之间若进程中断，记录会保留以避免操作编号被错误重用。
请求还使用 Redis 临时互斥锁，虽然不会在投递前修改互动关系或计数缓存，也不满足“完全不写共享 Redis”的严格字面要求。
同一用户对同一互动的结果未知时，客户端应先用原操作编号确认或重试，再提交相反操作；当前服务端没有持久顺序号来阻止
客户端在未知操作完成前提交新操作。

缓存失效和读取回填之间仍存在竞态：读取请求可能在业务提交前读到旧值，却在提交后的失效完成后才将旧值写入缓存。
该情况不会改变操作查询的数据库结果，但普通缓存读取可能在 TTL 内看到旧值；本次没有引入版本围栏。
需要在后续以版本或其他协调机制关闭该窗口，并用并发故障测试验证。

原生 RocketMQ 顺序消费者在失败时暂停队列，达到重试阈值后将任务和错误类型保存在 `interaction_failures` 中。
管理员可通过 `GET /api/v1/admin/interaction-failures` 查看未解决任务，通过
`POST /api/v1/admin/interaction-failures/{operationId}/retry` 从保存的记录恢复该任务；同帖消费在任务暂停期间被阻止。
失败会写入服务日志，运维应监控该表的 `PAUSED` 记录及 RocketMQ 消费积压。数据库不可用导致无法记录失败时，
消费者继续暂停并记录日志，不确认该消息。

## 未满足的验收：超过 Broker 保留期

失败任务本身的数据保存在 MySQL，可在原消息过期后由管理员恢复。但如果故障持续超过 Broker 保留期，
同一队列中**其他已受理但尚未消费**的消息也可能过期。绑定表不保存可安全重建这些消息的顺序，
因此不能保证这些操作最终应用或按原顺序重放；#185 的已受理请求最终可跟踪验收在此场景尚未满足。
不能仅依据已保存的失败任务宣布整个队列恢复。记录中的旧事件也不得在绕过暂停屏障的情况下手工重新投递。

复现需使用一次性、独立的 Broker 和数据库：使用顺序消费测试中的故障注入使操作 A 持续失败直到出现
`PAUSED`；在 A 暂停期间确认同队列操作 B 已获得发送确认但尚未应用；保持故障超过测试 Broker 配置的消息保留期，
并确保对应 CommitLog 文件滚动并被 Broker 清理；然后恢复 A、查询 B。若 B 的原消息已被清理，B 仍为 `UNKNOWN`，
当前实现不会从绑定表自动恢复它。测试环境必须确认文件确实被清理，单纯等待保留时间不保证活动文件被删除。

可选后续方案是持久保存所有已确认或结果未知的待处理操作及其可靠顺序，并在恢复时重投或按该顺序处理；
若要保证入口提交与待发送记录原子一致，需要另行评估 transactional outbox 及其与“Broker 明确拒绝时不受理”语义的取舍。
此方案不属于本次实现。现有定向测试覆盖数据库重复投递、旧消息重放、权限、缓存失效失败、真实 Broker 重试和队列暂停恢复；
超过保留期的场景尚未在本次测试中实测。
