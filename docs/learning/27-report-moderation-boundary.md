# 27 · 举报处置回到内容领域写入口

## 一、架构迁移全景

举报域原本既负责审核状态，又直接读取帖子、评论仓储，修改内容实体并驱逐帖子详情缓存。一次“确认举报”跨越了三个领域：

```text
ContentReportService
  ├─ CommunityPostRepository ── 直接改 CommunityPost
  ├─ CommunityCommentRepository ── 直接改 CommunityComment
  └─ TwoLevelCache ── 手工清 POST_DETAIL
```

本次把内容校验与处置收回内容领域：

```text
ContentReportService
  ├─ PostPublishingService.ensurePublished / deleteForModeration
  └─ CommunityCommentService.ensureReportable / deleteForModeration
       └─ 各自负责实体状态和提交后缓存失效
```

举报域现在只依赖举报仓储与两个内容领域服务。管理员接口、举报 DTO 和错误码保持不变。

## 二、关键难点解析

### 1. 领域边界不等于多包一层转发

如果举报服务继续查询实体、判断状态、再调用缓存，只是把仓储换成服务名，穿透仍然存在。新方法必须真正拥有规则：帖子是否可举报、评论是否已删除、处置后缓存哪个 key，都由所属领域决定。

评论缓存的是“所属帖子详情”，键必须取 `comment.getPostId()`；帖子举报则取 `postId`。这两个键不能统一成举报目标 ID，否则评论确认后帖子详情会继续展示旧评论。

### 2. 内容处置与审核状态必须同事务

`handle` 在同一个事务里完成：

1. 锁定举报行；
2. 校验仍为 `PENDING`；
3. 委托内容领域删除；
4. 保存 `CONFIRMED` 或 `REJECTED`。

缓存失效通过 `CacheInvalidationAfterCommit` 延迟到提交后。事务回滚时既不删除缓存，也不会广播幽灵失效。

### 3. 幂等不能代替并发互斥

目标已删除时再次处置应当安全返回，这是幂等；但两个管理员同时处理同一条 `PENDING` 举报仍需互斥。否则两者都可能通过状态检查，最终互相覆盖为不同结果。

举报仓储增加：

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<ContentReport> findByIdForUpdate(String id);
```

第二个事务拿到锁后会读到第一个事务提交的终态，返回 `REPORT_ALREADY_HANDLED`。

### 4. 测试接缝要证明边界，而不是只证明“能启动”

边界测试同时收集字段和构造参数，要求集合精确等于：

```text
ContentReportRepository
PostPublishingService
CommunityCommentService
```

确认用例使用记录型领域服务桩，证明帖子/评论分别委派到对应领域；404 用例通过真实领域校验方法验证原错误码；并发用例使用两个真实 Spring 事务竞争同一行锁。

## 三、简历 STAR 写法

**Situation**：举报确认绕过内容领域服务，直接修改帖子和评论实体。新增内容规则需要在作者写路径和审核写路径各实现一次，容易产生缓存和状态规则漂移。

**Task**：在不改变 API 的前提下，把内容处置收回所属领域，同时保证举报状态转换、缓存失效和并发互斥正确。

**Action**：新增帖子/评论领域处置入口；把举报依赖收缩到仓库与两个领域服务；使用悲观行锁原子化举报状态检查；补充边界、委派、404、幂等和双线程确认测试。

**Result**：举报域对内容仓储、实体和缓存的依赖归零；边界与委派单元测试 5/5，举报缓存集成现有 7 个用例，锁变异测试 RED→GREEN；47 个测试源码编译通过。容器结果由 GitHub CI Docker runner 复验，回滚断言直接读取帖子仓储以绕过预热缓存。

## 四、原理详解

确认举报的事务时序：

```text
handle BEGIN
  SELECT report FOR UPDATE
  check status == PENDING
  contentDomain.deleteForModeration
    load target
    mark DELETED
    register afterCommit cache eviction
  save report CONFIRMED
COMMIT
  evict L1
  delete L2
  publish invalidation
```

行锁在事务提交或回滚时释放。内容方法也标记 `@Transactional`，默认传播加入外层事务，因此举报保存失败时内容状态一起回滚。

不存在或已删除目标不做错误抛出：举报创建阶段严格返回 404；审核确认阶段保持幂等，允许管理员完成一条目标已被作者删除的历史举报。

## 五、面试八股文整理

**问：为什么不让举报服务直接删帖子？**

答：举报是审核流程，帖子状态和缓存属于帖子领域。直接跨域写会让作者删除与举报删除维护两套规则，后续媒体、事件或索引策略变化时审核路径容易漏改。

**问：为什么不用乐观锁？**

答：举报处理是低频管理员操作，冲突概率低但要求明确失败。悲观行锁实现简单，锁范围只覆盖单条举报，不需要新增版本列迁移；高风险热点写路径才更需要乐观重试或无锁方案。

**问：缓存为什么在提交后清？**

答：Redis 不在数据库事务里。事务未提交就清缓存，失败回滚后会出现旧值被清、新值未落库的空窗；提交后清能保证失效对应真实新状态。

**问：幂等和并发控制有什么区别？**

答：幂等让重复执行结果稳定，例如目标已删除仍可确认；并发控制阻止两个请求同时基于过期判断做决策。二者解决不同问题，不能互相替代。

## 六、技术选型对比

| 方案 | 判断 |
| --- | --- |
| 举报域继续直接操作仓储与实体 | 拒绝；分层穿透，规则重复 |
| 举报域调用内容领域处置方法 | 采用；职责清楚，缓存与状态规则只有一个入口 |
| 抽公共内容处置模块 | 暂不采用；当前只有帖子、评论两类，抽象成本高于收益 |
| 举报表加 `@Version` 乐观锁 | 可行但需迁移和重试；本场景更适合单行悲观锁 |
| 查询后检查 `PENDING`，无锁保存 | 拒绝；两个管理员可能同时成功 |

## 七、面试叙事模板

**30 秒版**：我修过举报服务的分层穿透。管理员确认举报时，它直接改帖子和评论实体并手清缓存。我把删除和校验收回帖子、评论领域，用悲观行锁保证举报只处理一次，再补边界、404、缓存和并发测试。

**2 分钟版**：这个项目的举报表负责审核状态，帖子和评论各有自己的领域服务。原实现为了处理方便，让举报服务直接拿两个仓储改状态，还手工清帖子详情缓存。问题是作者删除、审核删除和未来的媒体/事件规则会在多个入口分叉。我把行为改成 `deleteForModeration`，由内容领域自己判断幂等和决定缓存键；举报服务只检查审核状态并委派。事务仍在举报服务外层，缓存失效在提交后执行。review 时又发现“检查 PENDING 再保存”有并发覆盖窗口，于是加 `SELECT FOR UPDATE`，并用两个真实事务验证恰好一个成功。帖子报错 404、评论软删除、提前删除幂等和缓存 L1/L2 失效都进了测试。
