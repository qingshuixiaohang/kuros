# 切片 #10：服务拆分——用户域独立微服务 kuros-user

> 本切片是项目第一次**真实物理拆分**：把用户域（认证/会话/RBAC/资料/关注）从单体
> `kuros-backend` 拆成独立部署、独立数据库的 `kuros-user`，经 Nacos 服务发现 +
> OpenFeign 完成服务间调用。共 9 个子工单（split-01~09），分 Phase A（模块化重排）
> 与 Phase B（物理拆分）两阶段。本文是收口复盘。

## 1. 架构迁移全景

### 迁移前（切片 #9 完成时）
系统形态是"Gateway 正门 + 单体 backend"：网关 `lb://kuros-backend` 只有单一上游，
"服务发现 + 统一入口"的架构价值没兑现（没有第二个实例可均衡）。用户域与内容域
耦合在同一进程、同一数据库，暴露四个结构性矛盾：

1. **边界没有物理约束**：跨域调用零成本——内容服务 6 处直接引用 `CommunityUserRepository`，
   `ProfileService` 一个类同时注入用户/帖子/评论/收藏四个域的仓储；边界只能靠自觉。
2. **发布耦合**：任一侧改动都触发整体构建 + 全量回归 + 整体重启。
3. **资源与故障连带**：高频轻量认证与重 IO 内容共享同一进程线程池/连接池/内存。
4. **技术选型绑定**：媒体换存储、搜索上 ES 等局部演进会波及整个进程。

### 迁移后
- 新增平级工程 `kuros-user/`（独立库 `kuros_user`、容器 8080 / 宿主 8091），
  承载认证 + 验证码 + RBAC（四表 + StpInterface）+ 用户资料 + 关注关系 + 内部 API。
- backend 退化为**内容服务**：`user/` 包只剩资料端点壳（经 Feign 回填）+ `client/`
  （UserDirectoryClient/Facade/DTO）+ Redis-only 的 StpInterfaceImpl；V10 迁移 DROP 7 张用户域表。
- 网关新增 `kuros-user-auth`（`/api/v1/auth/**`）与 `kuros-user-follow`（`/api/v1/users/*/follow`）
  两条 `order(-1)` 优先路由，其余仍 → `lb://kuros-backend`。
- 组合视图（公开资料/个人中心/用户帖子列表）**留在内容域组装**，经 OpenFeign 取用户数据；
  依赖方向固定单向：内容域 → 用户域。
- 两服务共享同一 Redis + 同名 Cookie（`KUROS_SESSION`）+ 相同 SaToken 配置，登录态零迁移穿透。

## 2. 关键难点解析

### 2.1 为什么"先重排再拆分"，而不是直接抽
按技术层分包（api/config/domain/web/service）时，用户域的类散落在 6 个包里，拆分要
跨包"挑拣"，边界不可见、出错难定位。Phase A 先做**零行为变化的模块化重排**（整目录
端走），让边界显式化；Phase B 拆分时按目录整体迁移。两阶段各自可二分回退——重排
出问题回退重排，拆分出问题回退拆分，不会混成一团。这是一次"零风险的显式化投资"。

### 2.2 为什么先拆用户域（依赖方向的决定性作用）
用户域被全站依赖（帖子/评论作者、权限校验）且边界闭环（认证 + RBAC + 资料 + 关注）。
**先拆"被依赖方"使依赖方向天然单向**（内容域 → 用户域）。反例：先拆内容域会迫使
用户域反向 Feign 调内容域，制造 A↔B 双向依赖——启动顺序敏感、故障级联，微服务经典反模式。

### 2.3 组合视图的归属：拒绝双向依赖
`/users/{id}`、`/users/me/profile` 是跨域组合视图（用户字段 + 内容统计）。若归用户域，
用户域就要反向调内容域拿帖子/点赞数 → 双向依赖。**决策：组合视图留内容域组装**，
用户字段经 Feign 取、内容统计本地聚合。依赖始终单向。

### 2.4 跨库外键消失 → 一致性降级为服务契约
`kuros_user` 与 `kuros` 两库间无外键约束。一致性手段降级为：① seed 用相同 ID 对齐
（两侧 V2 种子逐字一致）；② Feign 失败降级占位；③ 生产事件驱动同步（留 RocketMQ 切片）。
backend 的 posts/comments 表里 `author_id` 变成"裸外键"（无 DB 约束，仅逻辑关联）。

### 2.5 两条**相反**的降级路线（split-08 的核心设计）
`UserDirectoryFacade` 收敛了两条语义相反的降级：
- **内容域列表**（`findAuthors`）：吞掉一切 RuntimeException 返空 map → 作者占位"用户"
  （保留 authorId），帖子列表/详情**照常 200 不 500**。理由：列表是浏览主路径，
  用户域抖动不该让整页崩。
- **资料页**（`requireUser`/`following`/`followers`）：失败即 503（ServiceUnavailable），
  未知 id → 404。理由：资料页主体就是用户数据，拿不到就该明确告知不可用，而非渲染空壳。

同一个 Feign 客户端，两种失败语义——按调用场景分流，是"防雪崩"与"不撒谎"的平衡。

### 2.6 批量回填消除跨服务 N+1
列表若逐条查作者 = 跨服务 N+1（一页 20 条打 20 次 Feign）。改为**整页一次 `findAuthors`**
（`@RequestParam("ids") List<String>` 编码为 `ids=a&ids=b`），详情走单元素 `batch(List.of(id))`。
跨服务调用的往返成本远高于本地查询，批量是拆分后的必修课。

### 2.7 锁-事务竞态在迁移中复活（split-08 终修）
`UserFollowService` 类级 `@Transactional` 让代理在方法体前开启事务、返回后才提交，而锁在
`finally` 释放——时序退化成 `unlock` 先于 `commit`，留下极窄窗口：启动稍晚的线程在赢家
已解锁、事务未提交时拿到锁，`existsById` 读不到未提交的行 → 重复 insert → 撞复合主键 → 500。
症状是并发测试**随机飘红**（CI run 35596400478 首轮命中、重跑即绿）。终修：去掉类级注解，
让 `TransactionTemplate` 在锁内自开自提交（`lock → tx → commit → unlock`），窗口结构性关闭。
教训："锁包裹事务"不能靠类级注解（它把 commit 推到方法返回之后），事务边界必须显式落在锁内。

### 2.8 跨服务测试的两条缝（免起全栈）
- **桩缝**：JDK 自带 `com.sun.net.httpserver.HttpServer` 模拟 kuros-user，Feign 的 `url`
  属性用 `@DynamicPropertySource` 覆盖为桩地址直连——不起 Nacos，秒级。桩带 `healthy` 开关
  专门验证降级路线。
- **服务发现缝**：Testcontainers 起真实 Nacos，测试内用 `NamingService` 把桩注册为
  `kuros-user` 实例，Feign `url` 留空走 `lb://` 真实链路。
- 坑：`HttpServer.stop()` **不关闭**调用方 `setExecutor` 传入的 executor；非守护线程池
  会挂住 Surefire fork JVM（"forked VM terminated without saying goodbye"）。修复双保险：
  守护线程工厂 + `close()` 里显式 `shutdownNow()`。

## 3. 简历 STAR 写法（含"原方案为何不行" + 收益量化）

- **S（情境）**：微服务项目有 Nacos 注册中心与 Gateway 正门，但上游只有单体 backend 一个
  实例，服务发现/统一入口的架构价值没兑现；用户域与内容域同进程同库，边界只靠自觉，
  发布耦合、故障连带。
- **T（任务）**：完成第一次真实物理拆分，把用户域拆成独立部署单元，要求**前端零改动、
  外部 API 契约不变、登录态不中断**，并留下可被面试深挖的决策链。
- **原方案为何不行**：① 继续单体——边界熵增没有刹车，任何一侧改动都整体重启；
  ② 一次性全拆——本项目无生产流量兜底，大爆炸式拆分风险不可控、无法二分回退；
  ③ 先拆内容域——会迫使用户域反向调用，制造双向依赖反模式。
- **A（行动）**：两阶段渐进拆分——Phase A 零行为变化模块化重排（整目录端走、可回退），
  Phase B 物理拆出 kuros-user（独立库 + Nacos 注册 + 网关分流）；组合视图留内容域、
  依赖单向；OpenFeign（超时 connect 1s / read 2s）+ 两条相反降级路线 + 批量回填消 N+1；
  跨库一致性从外键降级为"约定 ID + 服务契约 + TTL 兜底"；登录态经共享 Redis 会话零迁移穿透。
- **R（结果，可验证的结构性收益，非压测数字）**：
  - **边界物理化**：跨域数据获取从内容服务 6 处直接 `CommunityUserRepository` 引用，
    收敛为 1 个 Feign 接口（`UserDirectoryClient`）——越界只能走契约。
  - **用户域物理迁出**：backend 删除 16 个用户域文件 + V10 DROP 7 张用户域表。
  - **独立部署**：compose 可单独重启 kuros-user 而内容服务不中断。
  - **故障隔离**：停 kuros-user 后帖子列表/详情降级返回（作者占位"用户"）整页不崩、资料页明确 503。
  - **会话穿透**：经网关登录（user 写 Redis）→ 发帖（backend 读同一会话）→ 详情作者昵称经 Feign 回填，一条冒烟链路端到端验证。
  - **质量门**：backend 全量测试绿 + 跨服务双接缝测试 + 三服务 Nacos 注册校验，CI 五 job 全绿。
  - （性能类收益如独立扩缩容，留待压测切片以数据佐证，不做无依据表述。）

## 4. 原理详解

### 4.1 跨服务请求全链路
```
浏览器 ── Cookie: KUROS_SESSION ──▶ Gateway (:8080, Netty)
   │  RoutePredicateHandlerMapping
   │   /api/v1/auth/**      ─┐ order(-1) 优先
   │   /api/v1/users/*/follow ┴─▶ lb://kuros-user
   │   其余 /**             ─────▶ lb://kuros-backend
   ▼
kuros-backend (Tomcat, 容器 :8080)
   │  帖子详情需要作者昵称
   │  CommunityPostService → UserDirectoryFacade.findAuthors(ids)
   │     ▼ @FeignClient(name="kuros-user", url="${...:}")
   │  url 留空 → Spring Cloud LoadBalancer
   │     ▼ ServiceInstanceListSupplier ← NacosDiscoveryClient（gRPC 订阅）
   │  选中 kuros-user 实例 → GET /internal/v1/users/batch?ids=...
   ▼
kuros-user (Tomcat, 容器 :8080) ── 查 kuros_user 库 → 返回 UserBriefResponse 列表
   ▲
   └── 登录时：SaToken 把会话写进共享 Redis；backend 读同一 Redis 校验登录态
```

### 4.2 Feign url 留空 vs 注入桩地址
`@FeignClient(name="kuros-user", url="${app.feign.kuros-user.url:}")`：
- `url` 为空（默认）→ 走 `lb://kuros-user`，经 Nacos 服务发现 + LoadBalancer 选实例（生产/compose 链路）。
- `url` 注入具体地址（测试）→ 直连该地址，绕过服务发现（桩测试秒级、确定性）。
一个属性开关切换"真实发现"与"直连桩"，是跨服务测试可测性的关键设计。

### 4.3 会话为什么能零迁移穿透
SaToken 会话 Token 与权限数据存 Redis，Cookie（`KUROS_SESSION`）是 Host-only。两服务
共享同一 Redis + 同名 Cookie + 相同 SaToken 配置 → user 登录写的会话，backend 直接能读。
这是切片 #1"分布式会话"决策的远期回报：拆服务时登录态一行代码不用改。

## 5. 面试追问链回答清单（≥5 条）

**Q1：单体为什么不香了？拆分的触发点是什么？**
A：不是"单体不行"，而是单体的架构价值已兑现完毕、矛盾开始显现：网关只有单一上游
（服务发现空转）；跨域调用零成本让边界熵增没有刹车（内容服务 6 处直接引用用户仓储、
ProfileService 注入四个域的仓储）；发布耦合（改用户模块要重启内容服务）。触发点是
**前置积木就绪**——共享 Redis 会话（#1）、Nacos（#8）、Gateway（#9）缺一块拆完即断。

**Q2：为什么先拆用户域，而不是内容域？**
A：看依赖方向。用户域被全站依赖（作者、权限）且边界闭环；先拆"被依赖方"让依赖天然
单向（内容 → 用户）。先拆内容域会迫使用户域反向 Feign 调内容域，制造 A↔B 双向依赖
（启动顺序敏感、故障级联），是微服务经典反模式。

**Q3：为什么不是一开始就拆微服务？**
A：拆分有前置成本（分布式会话、注册发现、统一入口）。没有共享会话，拆完登录态就断；
没有注册中心，`lb://` 无从解析；没有网关，前端要逐个感知服务地址。所以路线是
Redis+SaToken → Nacos → Gateway → **再拆分**，顺序错了就是给自己挖坑。

**Q4：跨库一致性怎么保证？没有外键了怎么办？**
A：一致性从"DB 外键约束"降级为"服务契约"三件套：① seed 用相同 ID 对齐（两侧 V2 种子
逐字一致，author_id 裸外键逻辑关联）；② Feign 失败按场景降级（列表占位"用户"不 500、
资料页 503）；③ 生产环境的事件驱动同步（用户改昵称 → MQ 通知内容域失效缓存）留给
RocketMQ 切片，当前用 publicProfile 60s TTL 兜底。诚实说：这是 CAP 取舍，跨库强一致
成本过高，选择最终一致 + 明确降级。

**Q5：拆分的代价是什么？**
A：① 跨库无外键，一致性靠契约而非约束；② 跨服务调用引入网络往返（必须批量消 N+1）+
超时/降级/熔断的容错代码；③ 运维面变大（多一个服务的部署、监控、配置）；④ 分布式事务
缺位（关注 + 计数跨库时只能靠幂等 + 锁，不能靠 ACID）；⑤ 测试复杂度上升（要桩 + 服务
发现双缝）。收益是边界物理化、独立部署、故障隔离；代价是复杂度从"进程内"转移到"网络间"。

**Q6：拆分收益怎么验证？（可复现演示，非口头）**
A：四条可复现演示——① 边界物理化：跨域数据只能经 Feign 接口（代码层面 6 处直引收敛为 1 个 client）；
② 独立部署：compose 单独重启 kuros-user，内容服务不中断；③ 故障隔离：停 kuros-user 后
帖子列表降级返回（作者占位）整页不崩；④ 会话穿透：经网关登录 → 跨服务发帖 → 详情作者
昵称经 Feign 回填，冒烟脚本一条链路端到端断言。性能类收益（独立扩缩容）留压测切片用数据说话。

**Q7（加分）：组合视图为什么留内容域，不下沉到用户域？**
A：资料页 = 用户字段 + 内容统计（帖子数/点赞数/评论数）。若下沉用户域，用户域就要反向
调内容域 → 双向依赖。留内容域组装：用户字段经 Feign 取、内容统计本地聚合，依赖始终单向。
原则：**组合视图放在"依赖箭头下游"的那个域**，谁被依赖谁就不该反向感知调用方。

## 6. 技术选型对比

### 6.1 拆分节奏：模块化单体 vs 一次性全拆 vs 渐进式拆（本切片选渐进式）

| 维度 | 模块化单体 | 一次性全拆 | 渐进式拆（本项目） |
|---|---|---|---|
| 边界约束 | 逻辑分包，靠自觉 | 物理隔离，最彻底 | 物理隔离，逐域推进 |
| 风险 | 低（不拆） | 高（大爆炸，无生产流量兜底） | 中（每步可二分回退） |
| 回退粒度 | 整体 | 难（牵一发动全身） | 按工单/按阶段 |
| 前置要求 | 无 | 会话/注册/网关全就绪 | 同左，但可分步兑现 |
| 适用边界 | 小团队/边界稳定/无独立扩缩容需求 | 绿地项目/边界极清晰/团队微服务经验丰富 | 既有单体演进/边界逐步清晰/要可控风险（**本项目场景**） |

### 6.2 关键决策的备选方案（ADR 0003）

| 决策点 | 选定 | 拒绝的备选 | 拒绝理由 |
|---|---|---|---|
| 拆分方式 | 先重排再拆（两阶段） | 按技术层直接抽取 | 跨 6 包挑拣、边界不可见、难定位 |
| 组合视图归属 | 留内容域 | 挪到用户域 | 用户域反向调内容域 → 双向依赖反模式 |
| 公共代码 | 有纪律复制（rule of three） | 立即建 Maven common 模块 | 重复点仅 2 处未达 rule of three，过早抽象、复杂度翻倍 |
| 首拆域 | 用户域 | 先拆帖子/评论域 | 内容域被互动/举报/媒体深度引用，牵出整个内容域；用户域边界最清晰 |
| 跨库同步 | 约定 ID + 契约 + TTL 兜底 | 立即上 RocketMQ 事件驱动 | 正确但超范围，留后续切片 |
| 服务间调用 | OpenFeign 声明式 | RestTemplate/WebClient 手写 | 声明式接口即契约，配合 lb 与降级更内聚 |

## 7. 面试叙事模板

**30 秒电梯版**：我把一个单体后端按业务域拆成用户服务和内容服务两个独立部署单元。
做法是两阶段：先零行为变化地把按技术层分包重排成按业务模块分包，再物理拆出用户域——
独立库、Nacos 注册、网关按 API 前缀分流。服务间用 OpenFeign 调用，配超时和两条相反的
降级路线（列表占位不崩、资料页明确 503）；登录态靠共享 Redis 会话零迁移穿透双服务。
前端零改动、外部契约不变，一条"网关登录 → 跨服务发帖 → 作者信息回填"的冒烟链路端到端验证。

**2 分钟详细版**：在 30 秒版基础上补充——
① **为什么此刻拆**：前置积木（共享会话/Nacos/网关）就绪，网关单一上游让服务发现空转；
② **为什么先拆用户域**：先拆被依赖方，依赖天然单向，避免双向依赖反模式；
③ **两阶段的价值**：重排让边界显式化、整目录端走，两阶段各自可二分回退；
④ **跨库一致性**：外键消失后降级为"约定 ID + 服务契约 + TTL 兜底"，事件驱动留 RocketMQ；
⑤ **两条相反降级路线**：内容列表吞异常占位"用户"不 500、资料页失败即 503，按场景分流；
⑥ **真实踩坑**：锁-事务竞态在迁移中复活（类级 @Transactional 让 unlock 先于 commit，
并发测试随机飘红），终修是让事务在锁内提交；以及 JDK HttpServer 测试桩的 executor
线程泄漏会挂住 Surefire fork JVM；
⑦ **收益验证**：边界物理化（6 处直引收敛为 1 个 Feign client）、独立部署、故障隔离、
会话穿透，全部可复现演示，性能收益留压测切片用数据说话。
