# 30 · 最终浏览器基线修复

> 对应：最终发布集成验证中发现的前端回归。

## 一、架构迁移全景

发布前集成不能只统计 Playwright 发现了多少用例，必须从最终集成树实际执行。首次全量运行得到 124/128，四条失败分别暴露了两处产品问题、一处错误态语义混淆和一处过宽测试断言。规范 review 又补了一条普通 404 回归后，最终全量为 129/129。

修复没有引入新页面或新数据层，只恢复既有接缝：

- 首页 Feed 的 loading 文案真正成为 `role="status"`。
- 声骸详情只把 `404 ECHO_NOT_FOUND` 映射成“不存在”，普通 404 与其他错误继续展示“加载失败”。
- 同人请求隔离测试只统计带 `category=同人` 的帖子请求，避免把其他页面右栏的正常帖子请求误判为同人查询。

## 二、关键难点解析

### 1. 测试发现数不等于测试通过数

`playwright test --list` 只能证明测试文件可被解析。最终集成必须先执行完整浏览器套件，再把通过数写进状态页。首次串行执行直接找出了 4 个历史假绿。

### 2. 请求隔离要绑定业务语义

“其他社区页面不会请求同人帖子列表”不等于“其他页面不请求任何帖子列表”。资讯页右栏会正常请求 `/api/v1/posts?pageSize=40`；原测试把所有帖子请求都计入，导致页面正确行为被误判。

最小修法是只统计 `category=同人`，并继续为无关请求提供隔离响应。这个断言对应真正要保护的消费边界。

### 3. 404 与 500 是不同用户结果

声骸 API 的 `404 ECHO_NOT_FOUND` 表示资源不存在或已下架；500 或普通 404 表示服务故障。查询层只把明确的业务码转成空数据，其他异常继续抛出，页面据此分别显示固定不存在态和加载错误态。

### 4. 可访问状态需要实际语义属性

首页已经在等待数据时显示“正在整理漂泊者的最新内容…”，但普通 `div` 不会作为 live status 播报。补上 `role="status"` 后，测试通过真实的 accessibility tree 验证，而不是只匹配可见文本。

### 5. 临时 worktree 的构建边界

最终集成 worktree 的 `node_modules` 是从主工作区链接进来的 junction。Turbopack 将项目外目标视为超出文件系统根并 panic；Webpack 能正常解析同一依赖树。生产构建因此使用 `npx next build --webpack`，并在状态页明确记录这是临时 worktree 限制。

## 四、原理详解

声骸详情的数据状态分为三条路径：

```text
GET /echoes/{slug}
  ├─ 200 -> data -> render detail
  ├─ 404 ECHO_NOT_FOUND -> null -> missing state
  └─ other error -> throw -> explicit load-error state
```

首页 Feed 的等待路径直接映射到 accessibility tree：

```text
isPending
  └─ visible copy + role="status"
       └─ assistive technology announces the loading transition
```

## 五、面试八股文整理

**问：为什么 404 不在 Query 层当作普通错误？**

答：只有 `404 ECHO_NOT_FOUND` 是确定的业务结果。普通 404、500 或 503 都可能来自网关、代理或服务故障，不能伪装成资源已下架。查询层先按状态码和业务码共同归一化，页面才能稳定选择不存在态或错误态。

**问：为什么 Playwright 测试不能只拦截 URL 前缀？**

答：同一资源会被多个页面消费。断言必须对应需求约束的参数或响应语义，否则正常消费者的请求会制造假失败。

**问：为什么用 accessibility tree 验证加载文案？**

答：视觉用户能看到文本，不代表辅助技术会被通知。`getByRole("status")` 同时锁住文案和 live region 语义。

**问：为什么不修改仓库构建脚本绕过 Turbopack 问题？**

答：问题只存在于外部 junction 组成的临时 worktree。生产布局不需要改变，保留 Webpack 作为受支持构建路径并在验证记录中说明边界更小。

**问：为什么全局全量测试要串行？**

答：这轮问题不是并发本身造成的，但在 16GB Windows 主机上，多 worker 叠加 Next.js 冷编译会制造超时。先用单 worker 取得确定性基线，再把真实并发问题留给稳定性专项处理。

## 六、技术选型对比

| 方案 | 判断 |
| --- | --- |
| 只保留 `playwright test --list` | 拒绝；发现数不能证明浏览器行为 |
| 全量继续使用默认 worker 数 | 拒绝；16GB 主机在冷编译时容易 OOM 或触发 40 秒超时 |
| 同人测试拦截所有帖子请求 | 拒绝；会与首页和右栏的正常消费者冲突 |
| 只按 `category=同人` 统计 | 采用；对应待保护的业务边界 |
| 所有详情错误都显示“不存在” | 拒绝；会掩盖可恢复的服务故障 |
| 仅 `404 ECHO_NOT_FOUND` 返回空数据，其他错误保留异常 | 采用；业务结果与基础设施故障语义清晰 |
| 为临时 worktree 修改 Turbopack 配置 | 暂不采用；扩大代码面且无法代表正常依赖布局 |
