# 17 · 测试基线清洗：从 3 个红灯到零，以及一个被掩盖的生产 bug

> 提交范围：`1fd59bd` → `f9bd189`（8 个提交）

## 一、起点：一套带着红灯的测试

上一轮结束时，e2e 的状态是 **90 passed / 3 failed**。那 3 个失败已经存在很久，我之前多次用 `git stash` 复现、判定"与本次改动无关"，然后继续。

这一轮的第一件事就是查清它们。结论比预想的严重：

**三个失败的用例根本没有 mock 后端**，直接打 `http://localhost:8080`。后端不在运行时页面加载失败，三个用例全部超时。症状是"测试挂了"，真相是**环境缺失**。

这不是三个测试的问题，这是**基线被污染**的问题——我此前每一次"90 passed, 3 个既有失败无关"的结论，都建立在一个脏参考点上。

## 二、STAR 叙事

**Situation**：e2e 长期带 3 个红灯，被反复归为"既有失败"。后端全量测试此前也因为 Nacos 连接问题报过 6 个 error，同样被归为环境问题。

**Task**：把测试基线洗干净——让每个失败都有明确归属，要么修、要么证明真的与代码无关。

**Action**：
1. 给三个详情页用例补 mock（新增 `e2e/helpers/post-detail-mock.ts`），让它们不依赖后端是否在跑
2. 把 18 处 mock 的绝对 URL 改成通配，解除与客户端默认 baseURL 的隐性耦合
3. 跑后端全量测试，把 2 个失败查到底
4. 给前端补 vitest 单测层，并把 format:check 和单测接进 CI

**Result**：e2e **95 passed / 0 failed**（这套测试第一次真正零红灯）；后端全量 **168 测试零失败**；vitest 31 个单测；CI 前端 job 从 2 步扩到 4 步。

## 三、挖出的真 bug：游客打开首页会 401

后端全量跑出 2 个失败，都在 `InteractionBatchStateIntegrationTest`：

```
批量状态端点对游客匿名可达且返回全零   期望 200 实得 401
超过数量上限的批量查询被拒            期望 400 实得 401
```

根因：H-2 建的 `/api/v1/interactions/batch-states` **没进 SaToken 公开 GET 白名单**。白名单里 `/api/v1/posts/**` 那条注释写着"互动状态"，但指的是 posts 下的端点；批量状态是独立路径，从未被豁免。

**后果是用户可见的**：未登录用户打开首页，批量互动状态请求吃 401，前端降级到本地 demo 赞态——正是前端 H-1/H-2 改造想解决的那个问题，在后端还有一道没开的门。

**为什么之前没发现**：这个测试类此前没在全量 suite 里跑过；而前端 e2e 的 `page.route` mock 把后端整个替掉了，根本不打真接口。两层测试各自绿，合起来覆盖不到这条路径。

RED 验证：临时移除白名单条目，2 个用例立刻回到 401；加回后 8/8。

## 四、第二批修复

**`TwoLevelCache` 日志丢栈** — 7 处 `log.warn(..., e.getMessage())` 改成传入异常对象。SLF4J 见末尾是 Throwable 会自动附完整栈。缓存故障排查时能看到的只有这些 warn 行，丢栈等于丢掉异常类型和调用路径。顺带移除消息末尾的 `": {}"` 占位符——它会打印异常 toString，和 SLF4J 追加的栈重复。这条写进了 javadoc，防止后来人"补全"又加回去。

审计范围：全仓只有 `TwoLevelCache` 有这个问题，其他类都规范。

## 五、测试层建设

### e2e：从红灯到零

新增 `e2e/helpers/post-detail-mock.ts`，mock 帖子详情、评论列表、登录态、CSRF、批量互动状态。三个用例接入后不再依赖后端是否在跑。

**判断标准**：一个测试失败时，必须能说出"这是代码错了还是环境缺了"。答不出来就是测试本身有问题。

### 单测层：vitest 31 例

三个文件，覆盖的都是"纯函数 + 零单测"的部分：

| 文件 | 用例 | 重点 |
|---|---|---|
| `post-view.test.ts` | 12 | markdown 图片提取的边界、计数格式化 |
| `post-mapping.test.ts` | 12 | **toGuide 的四级媒体回退链** |
| `demo-mapping.test.ts` | 7 | 演示映射表的交叉一致性 |

`post-mapping` 那 12 个最有价值：回退链优先级写反在只有一条数据的用例里看不出来，所以每一级都断言了"下级存在时上级被忽略"。

`demo-mapping` 守的是 `post-view.ts` 注释里自己承认的风险——「新增演示帖漏同步一处就静默降级」。静默降级没有报错没有红灯，只是内容悄悄退回 demo 态。单测能做的就是钉住集合一致性：映射表里的 slug 和作者必须真实存在于 mock 数据。

### CI：前端 job 从 2 步到 4 步

补 `format:check` 和 `npm run test`。这两样都是这轮新引入的，不接进 CI 就等于发布链上看不到它们。放在 build 之前——格式和单测比构建快，先失败省时间。

## 六、环境与工具坑

### prettier 的 endOfLine 与 core.autocrlf 打架

配了 `endOfLine: "lf"`，当时 `--check` 全绿。但仓库 `core.autocrlf=true`，checkout 会把仓库里的 LF 转成工作区 CRLF，于是 prettier 认为 42 个文件不合规——**包括它自己刚格式化过的那些**。

假警报，但看起来像真的。改 `endOfLine: "auto"`，行尾归一交给 git，格式化工具只管缩进引号宽度。

### Playwright 复用旧 dev server（上一轮的坑，这轮确认）

`reuseExistingServer: true`，改了源码但测试跑的是旧 bundle。排查"console.log 不打印"这类现象前，先确认 server 是新的。

### 两个 mutation 不能塞进同一个联合变量

```ts
const mutation = kind === "like" ? likeMutation : favoriteMutation;  // TS 推断成 never
```

分开 await，不要硬转类型。

## 七、没做的事

**首页 Feed 没迁 react-query**（连续两轮的同一个结论）。它有复杂的降级语义：following tab 走 Redis ZSet cursor 分页，其他 tab 走 posts 接口，失败时 following 报错、其他降级到 mock。迁 infiniteQuery 会丢掉这套逻辑，而它是全仓最脆弱的组件且无测试护航。mutation 层的 invalidate 已经能作用到它依赖的批量状态查询，主要矛盾解决了。

**H-9 六页 mock 接真数据**仍卡在后端没有对应端点。

## 八、面试可讲的点

**Q：你怎么处理测试套件里长期存在的失败？**

先分清"代码错了"还是"环境缺了"——答不出这个分别的测试本身有问题。那 3 个 e2e 失败是后者，补 mock 让它们自给自足。但更重要的教训是：**长期红灯会污染基线**，我此前多次基于"3 个既有失败无关"下结论，其实参考点本身是脏的。

**Q：说一个被测试盲区掩盖的生产 bug。**

批量互动状态端点没进鉴权白名单，游客打开首页 401 降级到 demo 赞态。前端 e2e 用 mock 把后端整个替掉，后端测试类又没进全量 suite——两层各自绿，合起来覆盖不到。修的时候做了 RED 验证：移除白名单条目，2 个用例立刻失败。

**Q：为什么评论不做乐观更新？**

要处理回滚，复杂度高；而且评论排序归服务端，乐观插入的位置本来就是猜的。选择"提交中禁用 + 成功后重取"。
