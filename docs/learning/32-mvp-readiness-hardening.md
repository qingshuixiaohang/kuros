# 32：MVP 发布加固批次复盘

> 范围：#159 父工单下的 #160–#167。
> 基线：`origin/main` @ `f4f156dcbe796feae1213224a2902451518086f0`。

## 做完了什么

- 生产配置改为 fail closed：固定验证码、开发密码、示例 token 和缺失 SMS adapter
  都不能进入 production；Compose 只公开 gateway/frontend，内部端口只绑定回环。
- 帖子媒体形成上传、发布、编辑、删除、下架和定时清理闭环。清理前会修复仍被已发布
  帖子引用的 `DELETED` 资产，避免不变量损坏后图片永久 404。
- 关注流在取消关注时同步移除作者时间线；Redis 丢失后可由用户关系和数据库回填。
  同分游标改用完整 Redis member 作为第二排序键，跨作者边界不再只比较 postId。
- 推荐、最新和关注流统一由 React Query 管理分页、竞态、错误与缓存失效。真实帖子在
  互动状态 pending 或失败时禁用写操作，不再静默回落到本地演示 toggle。
- 攻略分类、资讯/声骸/角色详情、评论与举报分页及无障碍契约全部有页面级验收。
- Next 升级到 16.4.2，生产依赖审计为 0；Actions 升到受支持主版本；生产媒体域名
  只来自部署配置，恶意域不会被 Next 图片白名单放行。

## 真正踩到的坑

### 1. 错误测试可能把错误行为固定下来

菜单最初要求“自然 Tab 后继续落到下一个链接”，但 Issue #166 要求菜单关闭后焦点回到
触发按钮。实现与测试必须同时服从规格，不能因为现有 Playwright 是绿色就认为契约正确。

### 2. 同分游标要使用存储层的完整排序键

ZSet member 从 postId 改成 `authorId:postId` 后，游标仍只保存 postId。单作者同分测试
看不出问题；一旦同毫秒帖子来自不同作者，Redis 按完整 member 排序，而应用按 postId
过滤，就会跳项。解决办法是让游标携带完整 member，边界比较与 Redis 使用同一排序键。

### 3. 失败态、pending 和空态是三种不同事实

互动查询 pending 时不能假设“未点赞”；失败时也不能把真实帖子降级为本地演示写入。
列表加载中同样不能同时播报“同步中”和“空结果”。状态机必须显式覆盖 pending、
error、empty 和 ready。

### 4. 清理“跳过”不等于修复损坏的不变量

定时清理排除 published 引用是正确的，但如果资产已是 `DELETED` 而帖子仍发布，单纯
排除会让状态永久错误。清理任务需要先修复这一可证明的引用冲突，再处理可删除候选。

### 5. 离线构建不能依赖远程字体

`next/font/google` 让本地和受限网络中的生产构建依赖 `fonts.googleapis.com`。项目改用
本地系统字体栈，构建不再因为外网不可用而失败。

## 为什么这样做

- 生产安全采用启动期拒绝，而不是日志告警。错误配置应在接流量前失败。
- 外部对象存储不是事务资源，所以媒体可见性先提交、物理删除失败留给下一轮重试。
- 游标的不透明格式允许内部排序键升级；两键游标的第二个 token 继续由服务端解释。
- React Query 只保留服务端真相；本地 toggle 只留给无后端 ID 的演示内容。

## 验证策略

- 每个行为先写可复现 RED，再写最小实现；修复后重跑同一 seam。
- 后端一次只跑一个 Maven JVM，Testcontainers 使用工作区短临时目录。
- Playwright 固定单 worker；受影响 spec 先合跑，再做最终全量。
- 提交前必须重新跑格式化后的 `tsc`、ESLint、Vitest、format 和生产构建。

## 已知边界

- 生产 SMS provider、凭据和 HTTPS 证书仍是部署前置；代码只能保证缺失时 fail closed。
- 本地 `npm audit` 必须使用官方 registry，镜像的审计接口可能返回 `NOT_IMPLEMENTED`。
- Next standalone 在 Windows 沙箱中复制产物可能遇到 `EPERM`；提权后同一构建通过。
- 最终修订上的 Playwright 全量为 161/161；审查发现的 pending 写入、菜单焦点、
  跨作者游标与媒体引用修复均已包含在这次执行中。

## 下次如何更快

1. 合并候选时先跑该文件现有 spec，不要只跑新用例，避免旧契约与新实现冲突。
2. 对 Redis 复合 member、数据库引用关系这类“存储键即排序键”的地方，测试必须包含
   多作者/多类型交错数据。
3. 前端查询先画出 pending、error、empty、ready 四态，再决定按钮是否禁用。
4. 全量 Playwright 结束前不要提前更新状态文档；所有数字从最终修订的实际输出抄录。
