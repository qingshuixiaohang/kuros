# 28 · 媒体上传一致性与临时资产补偿

> 对应 Issue：[#149](https://github.com/qingshuixiaohang/kuros/issues/149)、[#150](https://github.com/qingshuixiaohang/kuros/issues/150)

## 架构迁移全景

旧上传流程先写对象存储、再保存媒体资产元数据。如果数据库写入失败，或进程在两次操作之间退出，对象存储中会留下数据库无法发现的孤儿对象；现有清理任务只能遍历数据库中的临时媒体资产，无法处理这类对象。

本次把顺序改为先持久化 `TEMPORARY` 元数据，再写一次对象存储。元数据保存失败时不触碰对象存储；对象写入失败时先删除可能已经写入的残留对象，删除成功才把资产标记为 `DELETED`，删除或状态保存失败则保留临时态等待清理，并始终向调用方传播原始 `FileStorageException`。上传 API 与成功响应字段保持不变。

## 关键难点解析

- **不可发现副作用**：对象存储写入不是数据库事务的一部分。只有先把存储键持久化，进程中断后运维工具才知道该去找哪个对象。
- **两个故障点**：元数据写入可能失败，对象写入也可能失败。前者处理为对象存储零副作用，后者必须先处理结果未知的残留对象。
- **补偿自身也会失败**：对象删除失败时不能把记录标成 `DELETED`；保留 `TEMPORARY` 才能让已有过期清理重试。补偿异常也不能覆盖主故障。
- **取消不是回滚**：本切片没有引入跨对象存储的分布式事务，只建立“任何对象写入前先有已提交数据库记录”的可发现性不变量。上传方法挂起调用方事务，临时元数据由仓储事务独立提交，避免外层长事务把可见性推迟到对象写入之后。
- **验证证据**：第一个 RED 为元数据失败时期望对象写入 0 次、实际为 1 次；复审补充的 RED 为 `put` 报错后没有删除残留对象，以及删除失败时仍把记录标成 `DELETED`。移除事务挂起传播后，独立连接只看到 0 条临时记录。修复后媒体域定向测试 10/10，后端应用级 Testcontainers 回归 38/38，`mvnw test-compile` 通过。
- **本机环境**：Windows 上 Testcontainers 需要显式连接 Docker Desktop 命名管道，并为 JDK 指定非 MSIX 虚拟化的 Unix-domain socket 临时目录。该参数只用于本机验证，不写入项目配置。

## 简历 STAR 写法

- **S**：图片上传同时写对象存储和媒体资产表，但两处没有共同事务。数据库失败时会留下无法被清理任务发现的孤儿对象。
- **T**：在上传 API 和成功响应不变的前提下，让每个可能写入的对象都先有可查询的元数据，并处理对象写入与补偿写入失败。
- **A**：调整为 `TEMPORARY` 元数据优先；元数据失败直接返回；对象失败先删残留对象，删除成功才写 `DELETED`，删除或状态保存失败保持临时态；同时传播原始 `FileStorageException`。
- **R**：媒体域定向测试 10/10 通过，覆盖零写入、成功顺序、同键残留对象删除、删除失败重试、外层事务可见性和既有清理行为；完整后端应用级 Testcontainers 回归 38/38 通过；`mvnw test-compile` 通过。

## 原理详解

```text
upload
  -> validate image and generate storage key
  -> DB: insert MediaAsset(status=TEMPORARY) and commit
  -> object storage: put(storageKey)
       success -> return existing response shape
       failure -> best effort delete(storageKey)
               success -> DB: status=DELETED
               failure -> keep DB: status=TEMPORARY for cleanup retry
               -> always throw original FileStorageException
```

如果进程在数据库提交后、对象写入前退出，数据库只剩一条临时资产。现有清理任务可以按创建时间发现它，而对象删除实现需要接受“对象尚不存在”的幂等删除。若对象已写入但响应前进程退出，临时资产同样可被发现。若 `put` 抛错后对象删除失败，记录必须保持 `TEMPORARY`，否则 `DELETED` 会让清理器永久跳过可能存在的残留对象。

## 面试八股文整理

1. **为什么不能先写对象再写数据库？** 数据库失败后没有存储键元数据，清理任务无法枚举未知对象，只能做昂贵且容易产生误删的全量对象盘点。
2. **为什么不使用分布式事务或事务消息？** 对象存储不是本地资源，强行引入伪事务会增加依赖与状态面；这里要保证的是失败后可发现、可重试，而不是跨系统原子提交。
3. **对象写入失败后为什么先删对象？** `put` 抛错不代表服务端没有收到完整或部分对象；结果未知时必须先用同一存储键做幂等删除。
4. **对象删除也失败怎么办？** 不能标记 `DELETED`，否则清理器不会再发现残留对象；保留 `TEMPORARY` 并记录告警，让后续过期清理重试，同时保持原始存储异常。
5. **进程在任意位置崩溃后如何收敛？** 元数据提交前崩溃没有对象；提交后崩溃有可发现的临时记录；对象成功但响应前崩溃仍是临时记录；两条路径都能交给清理机制。
6. **临时媒体资产和孤儿对象有什么区别？** 临时资产在数据库中有元数据，清理任务能发现；孤儿对象没有元数据，只能靠全量存储盘点发现。本次调整正是避免产生后者。

## 技术选型对比

| 方案 | 优点 | 缺点 | 适用边界与本项目结论 |
|---|---|---|---|
| 对象优先，失败后删除对象 | 成功路径少一次数据库前置写 | 元数据未提交时无法可靠定位对象，进程中断会产生不可发现对象 | 不满足可发现性，拒绝 |
| 元数据优先，失败后补偿 | 每个对象写入前都有可查询记录；兼容现有清理任务 | 需要处理补偿失败和中间态 | 本项目采用 |
| 对象存储与数据库分布式事务 | 理论强一致 | 外部存储支持不可控、成本高 | 不适用于当前自托管存储 |
| Outbox + 异步消费对象写入 | 可重试、可审计 | 上传变成异步流程，改变 API 语义且超出本切片 | 未来若改异步上传可评估 |

## 面试叙事模板

**30 秒版**：图片上传原来先写 MinIO 再写数据库，数据库失败会留下清理任务永远看不到的孤儿对象。我改成先提交临时媒体资产元数据，再写对象；对象失败时先删除可能残留的对象，删除成功才标记删除，删除失败保留临时态继续清理，同时始终返回原始存储异常。

**2 分钟版**：我先画出上传的双写失败窗口，确认对象存储无法和 MySQL 共享本地事务。原顺序的问题不是简单返回报错，而是数据库里连 storageKey 都没有，后台任务不可能知道该删除哪个对象。于是我把 `TEMPORARY` 元数据作为对象写入前的可发现性屏障，并挂起调用方事务让元数据先由仓储事务提交：数据库失败就不调用存储；存储失败时，`put` 的结果可能不确定，所以先用同一 key 做幂等删除。只有删除成功才把资产标成 `DELETED`；删除失败必须保留 `TEMPORARY`，让现有过期清理重试。最后抛出的始终是原始 `FileStorageException`。测试覆盖成功、零副作用、同键残留对象删除、删除失败、外层事务可见性和补偿保存失败；媒体定向 10/10 和完整后端应用级 38/38 均通过。
