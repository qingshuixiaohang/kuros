# 0006. 加固热点详情读取，并为列表提供游标分页

日期：2026-09-22

状态：已接受

## 背景

两个读取场景有不同成本。热门帖详情的缓存一旦过期，多个请求可能一起回库重建。帖子列表翻到很深的页码，则可能需要数据库定位并跳过大量旧结果，还可能额外计算总条数。

## 决策一：帖子详情

- **两级缓存。** L1 是每个后端进程自己的 Caffeine，L2 是多个实例共享的 Redis。先查 L1，再查 L2；两层都没有时才组装内容。L2 命中可回填 L1。
- **热点重建。** 同一篇帖的请求竞争同一把 Redis 锁。拿到锁的请求先再查一次 L2，避免前一个请求已重建却重复查库。其他请求短暂重试，仍未命中时可直接回库。因此锁减少正常重建时的重复查询，超时降级仍可能带来多次回库。
- **失效与空值。** 内容变更后使缓存失效，并通过 Redis 广播通知其他实例清理 L1。广播可能错过，短 TTL 限制旧值停留时间。对查不到的帖子短暂记录“查无此帖”，以免同一个无效 ID 每次都查库。
- **计数单独读。** 详情缓存保存正文、作者等内容字段。点赞和收藏数在组装响应时读取，避免内容缓存命中导致新点赞看起来没有生效。见 [ADR 0009](0009-post-interaction-read-boundary.md)。
- **独立详情请求使用短读事务。** 回源时在本地事务内取齐帖子、标签和媒体，归还数据库连接后，再经 Feign 查询作者资料。等待用户服务期间可让其他请求借到内容库连接。发帖和编辑调用详情时沿用已有写事务，以便读取本事务内的变更。

## 决策二：列表分页

| 请求方式 | 下一页怎么找 | 返回信息 |
| --- | --- | --- |
| 页码分页（`page`、`pageSize`） | 按页码计算要跳过的数量，可以直接跳到第 900 页 | 条目与页码元数据，需要时做总数查询 |
| 游标分页（`limit`、`cursor`） | 传上一页的排序边界，继续查更旧或排名更靠后的记录 | 条目、`nextCursor` 和 `hasMore`，省掉总数查询 |

`GET /api/v1/posts` 用是否传入 `limit` 区分两种方式。按时间排序时，游标由发布时间和帖子 ID 构成，两篇帖子同一时刻发布时仍能区分顺序。热度排序还包含互动计数，跨页期间计数变化时仍可能看到位置变化。关注流也支持游标，使用 Redis 时间线的分数与完整成员区分同分记录。游标减少按深度跳过结果的开销，实际耗时仍由索引、筛选条件和数据分布决定。

## 备选与代价

过期时直接返回旧值并后台重建可以减少等待，但用户可能看见旧内容，同时需要管理重建任务。本项目采用短等待和锁内重查。游标适合“加载更多”，页码仍保留给要跳页或显示总页数的调用方。

## 如何验证

详情场景比较同一热帖过期时的重建次数；分页场景分别检查取数、总数和实际查询计划。之前 `page=900&pageSize=10` 的 JMeter 请求走的是页码分支，计数 SQL 前后对照与页码、游标之间的对照是两组不同实验。

2026-11-24 本机用同一批 4,800 篇冷帖、32 并发，按「基线、短事务、短事务、基线」各运行。四轮响应内容一致。短事务把每轮平均连接占用从 9.77–11.52 ms 降到 3.77–4.13 ms，平均借连接等待从 18.20–22.11 ms 降到 0.29–0.30 ms。这些数据描述单机冷缓存短跑表现。
