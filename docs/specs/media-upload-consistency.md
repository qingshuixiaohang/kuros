# 媒体上传一致性与临时资产补偿

关联 Issue：[#149](https://github.com/qingshuixiaohang/kuros/issues/149)

## 问题

图片上传当前先写对象存储、再保存媒体资产元数据。如果元数据保存失败或进程在两步之间退出，对象存储里会留下数据库完全不知道的文件。现有临时资产清理只能遍历数据库中的临时记录，因此无法发现或删除这类孤儿对象。

成功上传与现有 REST 响应必须保持不变。本次修复的是失败与进程中断后的最终可收敛性。

## 方案

上传流程改为“先登记临时媒体资产，再写对象存储”：

1. 校验图片并生成唯一存储键。
2. 保存状态为临时的媒体资产元数据。
3. 元数据保存失败时立即失败，不写对象存储。
4. 元数据保存成功后写对象存储。
5. 对象写入失败时返回原有存储错误，并先尽力删除可能已经写入的残留对象。
6. 残留对象删除成功时把已登记资产标记删除；删除失败时保留临时态，交给现有清理任务重试。

即使进程在元数据提交后、对象写入前退出，也只会留下可被临时资产清理发现的记录，不会出现数据库无法追踪的物理对象。

## 用户故事

1. 用户上传成功时，仍获得与之前相同的媒体资产标识和 URL。
2. 元数据无法保存时，上传明确失败，不产生不可追踪的物理对象。
3. 对象存储写入失败时，上传明确失败；残留对象清理成功则资产标记删除，清理失败则保留可重试的临时记录。
4. 运维侧写入的每个对象都有可发现的媒体资产元数据。
5. 进程在元数据与对象写入之间中断时，临时记录可被后续清理发现。
6. 图片校验、内容所有权、帖子关联和响应字段保持不变。
7. 开发者无法在后续重构中无意恢复“先写对象、后写元数据”的顺序。

## 实现决策

- 沿用 `TEMPORARY`、`ATTACHED`、`DELETED` 三种媒体资产状态。
- 先保存临时元数据，再调用对象存储。
- 不建立跨越对象存储写操作和数据库写操作的伪事务；数据库先提交才是中断后可发现性的来源。
- 上传服务挂起调用方事务，使临时元数据在对象写入前由仓储事务独立提交。
- 临时元数据保存失败时不调用对象存储。
- 对象写入失败时先尝试删除同一存储键。删除成功才把临时资产标记删除；删除失败则保持临时态，交由清理任务重试。无论补偿结果如何都传播原始存储异常。
- 上传请求与响应契约不变。
- 自动定时清理与 XXL-JOB 接入不在本切片内。

## 测试决策

- 在媒体资产服务边界观察上传成功、失败和最终元数据状态。
- 最高优先级回归用例让元数据保存失败，并断言对象存储从未被调用。
- 第二个失败用例模拟对象已经写入但 `put` 返回错误，断言随后删除同一对象、标记资产删除，并传播原始存储异常。
- 第三个失败用例让对象删除也失败，断言资产保持临时态、残留对象仍可由清理任务发现，且删除异常不覆盖原始存储异常。
- 成功用例断言对象只写一次、资产为临时态、响应仍包含生成的标识和 URL。
- 现有 API 上传、所有权、帖子关联和临时清理测试继续作为回归防线。

## 不在范围内

- 接入 XXL-JOB 或新增调度器。
- 枚举对象存储以追查历史孤儿对象。
- 预签名直传、分片上传或图片处理。
- 修改帖子关联与媒体删除的状态转换。
- 清理本次改动之前已经失去元数据的历史对象；这需要独立的外部存储盘点。

## 补充说明

项目已有针对数据库可见临时资产的最佳努力清理。本切片让上传顺序与该清理机制相容。历史孤儿对象需要后续运维工具做一次对象存储盘点。
