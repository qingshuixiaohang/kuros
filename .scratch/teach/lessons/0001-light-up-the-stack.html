Lesson 0001 · 验证阶梯 L0

点亮全栈：亲手把 14 个服务跑起来

一切验证的地基。这一课不写一行代码，只做一件事——让系统在你手里活过来，并亲眼确认它真的活着。

学习路线说明（2026-10-20） 本课是可选的环境启动练习，不是当前功能学习主线的前置课。当前学习进度见 ../PROGRESS.md。
本课你要拿下的胜利 跑完后，你会在 4 个不同的界面亲眼看到系统在响应你：社区前端、网关健康检查、Nacos 服务列表、RocketMQ 控制台。这就是"实感"的起点——不再是"AI 说它 work"，而是"我看到它 work"。
分工更新（2026-10-03 起） 我们的分工调整为：你只负责把栈点亮，接口验证、数据库检查、冒烟测试由 AI 在跑起来的系统上执行。CI 已改为手动触发，日常验证不再依赖它。

compose 现在有两种模式：默认 docker compose up -d 只起 9 个中间件（后端用 IDEA 裸跑，仓库自带 .run/ 一键启动配置，或 cd front && npm run dev 起前端）；docker compose --profile full up -d --build 才是本课原来的 14 服务全家桶（演示/体检用）。本课流程照旧，但第 3 步命令记得带 --profile full。
为什么从这一课开始 你之前没有实感，是因为从没看过系统真正运行的样子。所有更高级的验证（Swagger、消息轨迹、跑测试）都要求栈先在跑。所以第一步永远是：把它点亮。

动手步骤

  1. 启动 Docker Desktop 你来做 现在你的 Docker 守护进程是关的（我刚探测过）。从开始菜单打开 Docker Desktop，等右下角鲸鱼图标从"跳动"变成"静止/绿色"，表示引擎就绪。然后在 PowerShell 里确认： 
    docker info
    看到这些就说明引擎活了 
    Server:
 Server Version: 29.7.2
 Operating System: Docker Desktop
 ...（不再报 "failed to connect to the docker API"）
    如果还报错 说明 Docker Desktop 还没完全启动，多等 20~40 秒再试。这一步只能你手动点——它是图形程序，我无法代劳。
  2. 确认环境变量已就位 你来做 项目根目录已有一个 .env（compose 会自动读它）。我们要确认"演示登录固定验证码"是开的，这样第 4 步你能顺利登录： 
    # 在项目根目录 g:\kuros-web 下执行
Select-String -Path .env -Pattern "APP_AUTH_DEV_CODE"
    期望看到（两行） 
    APP_AUTH_DEV_CODE=123456
APP_AUTH_DEV_CODE_EXPOSED=true
    如果这两行不存在或被注释掉，登录时就要收真实短信验证码（收不到）。把结果贴给我，需要的话我给你补上。
  3. 一键启动整个栈 你来做 这是核心命令。-d = 后台运行（不占着终端）；--build = 首次需要构建 backend/user/gateway/frontend/es-ik 这几个自定义镜像： 
    docker compose up -d --build
    耐心提示 首次运行会很慢（5~15 分钟）：要拉十几个基础镜像 + 构建 5 个自定义镜像 + 编译 Java。终端会刷一大堆日志，这是正常的。之后再启动就快了（镜像已缓存）。让它跑完，直到提示符回来。
  4. 盯着服务逐个变绿 你来做 反复运行下面这条，观察 STATUS 列从 starting 逐渐变成 healthy： 
    docker compose ps
    全部就绪时大致长这样（STATUS 列都是 healthy / Up） 
    NAME                    SERVICE              STATUS
kuros-mysql             mysql                Up (healthy)
kuros-redis             redis                Up (healthy)
kuros-minio             minio                Up (healthy)
kuros-nacos             nacos                Up (healthy)
kuros-backend           backend              Up (healthy)
kuros-user              user                 Up (healthy)
kuros-gateway           gateway              Up (healthy)
kuros-rocketmq-*        rocketmq-*           Up
kuros-elasticsearch     elasticsearch        Up (healthy)
kuros-canal-server      canal-server         Up
kuros-frontend          frontend             Up
    启动顺序有讲究 MySQL/Nacos/RocketMQ 会先起，backend/user/gateway 依赖它们，会等到依赖 healthy 才启动（compose 的 depends_on + healthcheck 在编排这件事）。所以变绿是有先后的，不用慌。
    如果某个服务卡在 starting 超过 2 分钟或反复重启，用排障三件套看它的日志： 
    docker compose logs -f backend   # 换成卡住的那个服务名
  5. 肉眼确认 4 个界面 你来做 · 这就是实感 在浏览器里逐个打开，每个都截图/记下你看到了什么：
    打开这个网址你应该看到它证明了什么
    localhost:3000 鸣潮社区首页（帖子列表） 前端 + 网关 + backend + MySQL 整条读路径通了
    localhost:8080/actuator/health {"status":"UP"} 网关进程活着（Actuator 健康端点）。注意：它只反映网关自己，不聚合 backend/user 健康——那要看各自 :8090/:8091 的同名端点
    localhost:8081（Nacos） 控制台里 backend/user/gateway 三个服务已注册 服务注册发现生效——网关才知道该把请求转给谁
    localhost:8082（RocketMQ） Dashboard 里能看到 Topic 列表 消息中间件活着——发帖异步化 / CDC 都靠它
    Nacos 登录 账号 nacos / 密码 nacos123（由 docker/mysql-init/30-nacos-admin-user.sql 种子注入）。注意：v3 控制台有独立鉴权开关，即使 NACOS_AUTH_ENABLE=false 也要登录——它和服务端 OpenAPI 鉴权是两回事。报错 “User not found” 其实是“用户不存在或密码错”的合并提示（防枚举），登不进先检查密码是不是 nacos123。

本课收尾：你解锁了什么

  • 我能独立启动 Docker Desktop 并确认引擎就绪
  • 我跑通了 docker compose up -d --build，看着 14 个服务逐个变 healthy
  • 我在浏览器里亲眼看到前端、网关健康、Nacos 注册、RocketMQ 控制台 4 个界面
  • 我知道卡住时怎么用 docker compose logs -f <服务> 排查

现在系统在你手里活着了。下一课（L1）我们就在这个跑起来的栈上，亲手登录→发一个帖子→再把它搜出来，同时打开控制台看这个动作背后消息是怎么流的。

卡在哪一步，直接告诉我 把报错信息或 docker compose ps 的输出贴给我，我帮你判断是哪个服务、什么原因。不要自己硬扛——第一课的目标是"跑通"，不是"独自排障"。
